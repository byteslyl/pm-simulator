# CareerCraft 项目决策模拟器

## 产品共识文档 5.0

> 团队内部共识版本
> 更新日期：2026 年 7 月 22 日

## 30 秒结论

CareerCraft 是一款面向管理科学与工程相关课程的复杂项目决策仿真实训工具。

它不试图覆盖管理科学与工程专业的全部课程，也不是泛化的管理学模拟器、职业培训平台或多 Agent 聊天产品。

CareerCraft 聚焦一个明确的能力缺口：

> 学生如何在信息不完全、多方目标冲突和资源有限的条件下，主动获取证据、识别约束、比较方案，作出可解释的管理决策，并承担决策产生的动态后果。

产品通过多个持有不同信息、利益诉求和执行约束的 AI 干系人，构建可控的项目决策环境。学生需要将对话转化为事实、目标、约束、方案和风险，并提交正式决策。

系统不只评价最终答案，还会记录学生找了谁、获得了什么信息、验证了哪些冲突、遗漏了哪些约束，以及决策如何改变项目状态，并据此提供可追溯、可解释的复盘反馈。

**多 Agent 是分散信息与利益冲突的实现手段，复杂项目决策闭环才是产品本体。**

# 二、产品定位

## 2.1 一句话定位

> CareerCraft 是面向管理科学与工程相关课程的复杂项目决策仿真实训工具，重点训练学生在信息不完全和多目标约束下获取证据、比较方案并承担决策后果。

## 2.2 我们解决的唯一核心痛点

传统管理案例通常会预先整理好问题背景、角色观点和所需信息。学生更多是在获得相对完整的信息后分析方案、撰写报告或回答问题。

但真实管理决策往往要求决策者先完成以下工作：

* 发现真正需要解决的问题；
* 判断应该找哪些干系人；
* 主动获取和验证信息；
* 区分客观事实、主观判断、预测和利益立场；
* 识别资源、时间、质量、风险等约束；
* 在多个无法同时满足的目标之间作出取舍；
* 对决策后果负责并进行复盘。

因此，CareerCraft 聚焦的核心痛点是：

> 传统静态案例信息相对完整、角色功能扁平、决策缺少动态后果，难以训练学生在信息不完全、多方目标冲突和资源有限条件下完成真实、可解释的管理决策。

## 2.3 我们不是什么

| 我们不是什么             | 原因                                                         | 正确理解                                                     |
| ------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 管理科学与工程全课程平台 | 一个数字产品场景无法代表运筹学、系统工程、供应链、信息管理等全部方向 | 聚焦专业中的复杂项目决策训练能力                             |
| 泛管理学模拟器           | 过度泛化会失去明确用户、课程入口和评价标准                   | 首发服务管理科学与工程相关课程，未来可扩展到其他管理场景     |
| AI 聊天或角色扮演游戏    | 聊天本身不是学习目标，角色好感也不是最终结果                 | 对话用于获得决策证据，最终必须形成方案并承担后果             |
| 职业培训平台             | 数字产品项目只是教学载体，不是职业培训目标                   | 通过数字产品项目承载信息获取、约束识别、风险分析和多目标权衡 |
| 单纯的经营沙盘           | 传统沙盘通常侧重结果指标和资源配置                           | CareerCraft 同时评价信息路径、决策证据、约束识别和后果解释   |
| AI 自动打分工具          | 大模型评分存在不稳定、不可解释和幻觉风险                     | 使用规则结果、过程证据和 LLM 辅助反馈的混合评价              |
| 存在唯一标准答案的选择题 | 真实管理问题通常存在多种可行方案                             | 场景允许多种可辩护方案，但不允许任意答案                     |

# 三、用户、采用者与使用场景

## 3.1 三类核心角色

### 学习者

正在学习以下相关课程的本科生或研究生：

* 项目管理；
* 管理决策；
* 风险管理；
* 信息系统项目实践；
* 管理信息系统；
* 系统工程；
* 创新与产品实践。

学生通常已经知道基础概念和常用工具，但缺少在动态情境中综合使用这些知识的机会。

### 课程采用者

包括：

* 任课教师；
* 实验课教师；
* 课程负责人；
* 创新实践或竞赛指导教师。

教师的核心任务不是陪学生逐段聊天，而是：

* 快速布置一个与课程目标相关的仿真案例；
* 查看学生的决策过程和关键证据；
* 识别学生的典型错误；
* 组织课堂讲评和复盘讨论；
* 判断学生是否具备迁移性的决策能力。

### 采购或决策者

长期可能包括：

* 学院；
* 实验教学中心；
* 专业负责人；
* 数字化教学平台负责人；
* 创新实践中心。

首版竞赛 MVP 不验证完整商业采购流程，但必须验证教师是否愿意把产品用于真实教学活动。

## 3.2 典型使用场景

* 课程实训；
* 课堂案例后的进阶训练；
* 学生独立练习；
* 实验教学展示；
* 管理决策竞赛；
* 项目管理课程作业；
* 教师组织的课堂复盘活动。

## 3.3 核心使用任务

学生需要在有限时间和资源下：

1. 理解初始任务；
2. 识别关键干系人；
3. 主动访谈并获取信息；
4. 验证互相冲突的信息；
5. 明确目标、约束和决策边界；
6. 比较多个候选方案；
7. 提交决策、依据和执行预案；
8. 观察后果并完成证据化复盘。

## 3.4 首版最小教师价值

首版可以暂不建设完整教师后台和班级管理系统，但必须提供以下最小教师交付物：

* 可导出的学生个人复盘报告；
* 教师版场景说明；
* 场景目标与课程能力映射；
* 典型错误和课堂讨论问题；
* 场景真值、规则和推荐讲评重点；
* 能够展示学生证据链和关键遗漏的结果页面。

“不做教师后台”不等于“不提供教师价值”。

# 四、教学目标与能力模型

CareerCraft 只围绕四项可观察、可记录、可反馈的能力设计。

沟通能力不作为独立的“好感度玩法”，而必须服务于信息获取、冲突澄清和决策推进。

| 核心能力       | 学生需要完成的行为                                       | 系统可观察证据                                             |
| -------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| 信息获取与验证 | 判断找谁、问什么；区分事实、预测和立场；交叉验证冲突信息 | 访问角色、提问路径、关键事实获取率、信息来源、冲突验证记录 |
| 问题结构化     | 识别目标、硬约束、可控变量、干系人和方案边界             | 约束清单、决策表单、变量遗漏、方案可行性                   |
| 权衡与风险决策 | 在时间、资源、收益、质量和风险之间比较方案               | 方案比较、资源计算、风险判断、最终选择和执行预案           |
| 证据化复盘     | 解释决策逻辑，识别错误假设和关键转折，提出改进           | 证据引用、反事实分析、遗漏说明、二次决策变化               |

## 4.1 能力闭环

> 主动获取信息
> → 验证事实和立场
> → 结构化问题
> → 比较候选方案
> → 作出决策
> → 观察动态后果
> → 基于证据复盘
> → 迁移到新的相似任务

## 4.2 与管理科学与工程相关课程的映射

| 场景行为               | 对应能力           | 相关课程或知识方向     |
| ---------------------- | ------------------ | ---------------------- |
| 识别工期、资源与依赖   | 项目计划与资源配置 | 项目管理、系统工程     |
| 判断风险概率和影响     | 风险识别与风险响应 | 风险管理、决策分析     |
| 比较多个目标和方案     | 多目标权衡         | 管理决策、多属性决策   |
| 处理干系人冲突         | 项目治理与组织协调 | 项目管理、组织管理     |
| 获取和验证信息         | 信息支持与证据判断 | 管理信息系统、决策支持 |
| 观察局部决策的连锁后果 | 系统思维           | 系统工程、复杂系统管理 |
| 进行反事实复盘         | 决策改进           | 管理决策、实验与评估   |

产品不通过罗列课程名称证明专业性，而通过场景行为与可观察能力之间的对应关系证明教学价值。

# 五、核心体验闭环

每一项产品功能都必须回答：

> 它是否让学生更接近一次真实、可评估、可复盘的管理决策？

| 阶段            | 学生行为                         | 产品机制                                 | 教学意义                         |
| --------------- | -------------------------------- | ---------------------------------------- | -------------------------------- |
| 1. 接收任务     | 阅读背景、目标和截止时间         | 场景简报，只提供必要公开信息             | 不替学生预先定义完整问题         |
| 2. 发现信息源   | 判断需要访问哪些角色             | 多角色入口、角色职责与利益差异           | 训练干系人识别                   |
| 3. 访谈与验证   | 提问、追问、交叉验证             | 角色私有信息、条件披露、可信度和信息冲突 | 训练主动信息获取                 |
| 4. 建立决策模型 | 整理事实、目标、约束和候选方案   | 信息板、约束表、风险矩阵、资源计算       | 将聊天转化为决策结构             |
| 5. 阶段性判断   | 在信息不完整时作出中间决策       | 决策节点、资源消耗、状态更新             | 训练动态调整，而不是只做终局选择 |
| 6. 提交最终决策 | 选择方案并说明依据和预案         | 硬约束检查、方案提交、承诺锁定           | 迫使学生完成真实取舍             |
| 7. 观察后果     | 接收项目状态、角色反应和结果变化 | 状态变量、事件分支、因果传导             | 看到局部选择的长期影响           |
| 8. 证据化复盘   | 解释得失并进行二次判断           | 过程回放、遗漏信息、评分证据、反事实分析 | 将体验转化为可迁移能力           |

# 六、场景设计原则

## 6.1 场景不是剧情，而是可计算的决策系统

每个场景必须包含：

* 明确但不完整的初始任务；
* 多个具有不同信息和利益的干系人；
* 可验证的客观事实；
* 可能存在偏差的判断和预测；
* 明确的硬约束；
* 可以权衡的软目标；
* 至少两种逻辑上可辩护的方案；
* 会随决策变化的项目状态；
* 可追溯的因果链；
* 能够定位具体错误的复盘机制。

## 6.2 多解，但不允许任意解

CareerCraft 不设置唯一最优答案，但并不意味着所有答案都成立。

每个场景必须区分：

### 硬约束

可以由确定性规则判断，例如：

* 预算上限；
* 最低质量要求；
* 可用人力；
* 时间窗口；
* 法规、安全或合规红线；
* 必须满足的依赖条件。

违反硬约束的方案属于不可执行方案。

### 软目标

允许根据风险偏好、组织目标和价值权重进行不同取舍，例如：

* 短期收益；
* 上线速度；
* 长期技术债；
* 用户体验；
* 团队支持；
* 品牌风险。

多个方案可以同时合理，但必须满足基本可行性，并用已获得的证据解释取舍。

## 6.3 场景真值表

每个场景必须维护一份统一的内部真值表，作为以下模块的共同数据源：

* Agent 提示词；
* 信息权限；
* 状态计算；
* 事件分支；
* 评分规则；
* 复盘反馈。

场景真值表至少包含：

| 内容       | 说明                                     |
| ---------- | ---------------------------------------- |
| 客观事实   | 场景中确定成立且不应随模型生成变化的信息 |
| 信息持有者 | 哪些角色知道哪些事实                     |
| 信息权限   | 哪些信息角色可以披露，哪些不得披露       |
| 信息性质   | 事实、预测、立场、假设或传闻             |
| 可信度     | 信息是否准确、过期、有偏差或需要验证     |
| 决策价值   | 该信息会影响哪个方案、约束、风险或状态   |
| 披露条件   | 学生需要满足什么条件才能获取             |
| 状态影响   | 信息或决策会如何改变项目状态             |
| 冲突关系   | 哪些信息或利益之间存在有意冲突           |
| 评分关联   | 哪些行为会影响哪些评分维度               |

## 6.4 隐藏信息必须具有决策价值

隐藏信息不能只是彩蛋。

获得隐藏信息后，应至少改变以下一项：

* 方案可行性；
* 风险判断；
* 资源分配；
* 执行顺序；
* 应急预案；
* 干系人策略；
* 最终决策。

关键红线信息不能只依赖某一句精确提示词获取。

原则上：

* 关键事实至少有两条合理获取路径；
* 角色应给出值得追问的弱信号；
* 系统评价学生是否识别问题，而不是是否猜中关键词；
* 失败的第一次提问不应直接导致无法完成任务。

## 6.5 信息获取必须有机会成本

如果学生可以无成本地逐一问完所有角色，信息不完全就失去意义。

访谈机会成本可以通过以下机制体现：

* 总时间预算；
* 每次访谈消耗时间；
* 分析、会议、访谈和决策共享同一资源；
* 部分角色响应存在延迟；
* 重复信息不会带来额外收益；
* 某些角色需要已有证据才能展开深入讨论；
* 中间事件会改变可访谈对象和决策窗口。

机会成本必须服务于资源配置训练，不能退化为简单限制对话次数。

# 七、Agent 设计与可信边界

## 7.1 Agent 是分散信息源，不是产品本体

角色数量不固定。

每个角色必须至少承担一种不可替代功能：

* 掌握一类关键事实；
* 代表一种利益目标；
* 拥有一种决策权；
* 承担一种执行约束；
* 提供一种必要的专业判断。

如果删除某个角色不会改变学生的决策路径、信息结构或利益冲突，该角色不应进入首版。

## 7.2 Agent 可信性红线

1. Agent 不得创造场景真值表以外的关键事实；
2. Agent 只能访问其权限范围内的信息；
3. 客观历史事实不能因对话方式不同而随意变化；
4. 立场、判断、预测和态度可以变化，但必须符合角色设定；
5. 有意设计的信息冲突必须能够追溯到场景真值表；
6. 非预期事实矛盾必须被系统记录；
7. Agent 不得直接替学生完成最终决策；
8. Agent 不得泄露其他角色的私有信息；
9. 评估模式应尽量保证相同输入下的结果稳定；
10. 场景结果优先由确定性规则计算，不依赖大模型临时编造。

## 7.3 信息冲突的三种类型

| 类型     | 示例                              | 教学作用         |
| -------- | --------------------------------- | ---------------- |
| 事实冲突 | 不同角色提供的数据不一致          | 训练交叉验证     |
| 预测冲突 | 技术认为风险高，运营认为影响可控  | 训练不确定性判断 |
| 利益冲突 | 市场追求按时上线，QA 追求质量保障 | 训练多目标权衡   |

产品必须区分“教学设计中的有意冲突”和“大模型产生的非预期矛盾”。

## 7.4 关系反馈原则

后台可以维护连续的关系状态，但前台优先展示可理解的行为信号，例如：

* 开始愿意披露更多细节；
* 对学生的承诺产生怀疑；
* 认为学生忽视了本部门风险；
* 愿意支持有限发布方案；
* 拒绝为未验证的计划背书。

不建议在核心流程中持续展示 0–100 的精确信任分。

关系状态不得成为关键事实的唯一获取钥匙。角色拒绝披露时，应提供可解释的原因和改进方向。

# 八、首发标杆场景

## 8.1 场景名称

> 上线前夜：Go / Delay / Limited Release 决策

## 8.2 为什么优先选择该场景

该场景同时具备：

* 明确时限；
* 多角色利益冲突；
* 可量化风险；
* 不可兼得的方案；
* 可计算的资源约束；
* 明显且连续的决策后果；
* 与项目管理、风险管理和管理决策课程的关联。

## 8.3 场景背景

产品计划次日上线，并配合已经承诺的市场活动。

但测试尚未完全结束，核心接口存在不确定风险，研发和测试资源有限。延期会造成商业损失，强行上线可能带来线上事故。

学生需要在限定时间内提交以下方案之一，或提出满足规则的组合方案：

* Go：按计划全面上线；
* Delay：延迟上线；
* Limited Release：有限范围发布或灰度上线。

## 8.4 首版角色

首版优先设置 4 个核心角色：

1. 技术负责人；
2. QA 负责人；
3. 运营或市场负责人；
4. 业务负责人或 CEO。

数据分析能力可以由系统信息面板、运营角色或独立数据报告承载，避免为了展示多 Agent 而增加角色。

Mentor 不参与决策过程，只在复盘阶段出现。

## 8.5 分散信息示例

* 技术债严重程度；
* 核心接口的故障概率；
* 缺陷是否可稳定复现；
* 完成修复需要的人天；
* 活动延期损失；
* 当前外部承诺；
* 预期上线收益；
* 可灰度的用户范围；
* 回滚需要的时间；
* 组织对不同风险的容忍程度。

## 8.6 硬约束示例

* 可用研发与测试人天；
* 市场活动时间窗口；
* 最低质量阈值；
* 回滚准备要求；
* 安全或合规红线；
* 预算限制；
* 关键依赖是否完成。

## 8.7 学生产出

学生最终需要提交：

* 关键信息清单；
* 信息来源和可信度判断；
* 目标与硬约束；
* 风险矩阵或简化决策树；
* 至少两种候选方案比较；
* 最终决策；
* 决策依据；
* 应急预案；
* 关键干系人沟通方案。

## 8.8 动态后果示例

* 按时稳定上线；
* 上线后出现事故；
* 延期但避免重大损失；
* 有限发布成功；
* 灰度范围选择不当；
* 内部支持下降；
* 团队信任受损；
* 技术债增加；
* 市场活动效果下降；
* 用户投诉和后续修复成本上升。

## 8.9 场景最低质量标准

一个可进入产品的场景必须满足：

1. 至少存在两种逻辑上可辩护的方案；
2. 至少有 3 条会显著改变决策的隐藏信息；
3. 至少有 2 组事实、预测或利益冲突；
4. 至少存在 1 条明确硬约束；
5. 最终结果由已获得信息、决策方案和执行预案共同决定；
6. 关键事实不能依赖唯一精确问法；
7. 复盘能够指出具体遗漏和因果关系；
8. 场景可以在目标时间内完成；
9. 同一输入下的核心状态结果可复现；
10. 场景能够明确映射到课程能力。

# 九、评估设计

## 9.1 核心原则

> 评价学生如何作出决策，而不只是评价最终答案写得像不像。

评估采用：

> 确定性规则结果
>
> * 结构化过程证据
> * LLM 辅助解释

AI 不应单独决定全部分数。

## 9.2 四层评价结构

| 评估层       | 核心问题                             | 主要方法                                       |
| ------------ | ------------------------------------ | ---------------------------------------------- |
| 结果与硬约束 | 方案是否可执行，是否越过红线         | 规则引擎检查资源、时间、依赖和风险阈值         |
| 信息过程     | 是否找到关键角色并获得、验证关键证据 | 关键事实获取率、来源多样性、冲突验证、访谈成本 |
| 决策推理     | 是否明确目标、约束并比较多个方案     | 决策表单、方案比较、计算结果、证据引用         |
| 复盘迁移     | 是否识别错误假设并提出下一次行动     | 反事实分析、二次决策、平行任务表现             |

## 9.3 确定性评价内容

以下内容优先由规则判断：

* 是否违反预算；
* 是否超过工期；
* 是否满足最小质量要求；
* 是否遗漏必需依赖；
* 风险是否超过不可接受阈值；
* 方案与执行预案是否一致；
* 决策是否引用了实际获得的信息；
* 是否使用了不存在或无权限的信息。

## 9.4 LLM 辅助评价内容

LLM 可以用于：

* 解释学生取舍是否清晰；
* 判断复盘是否具体；
* 识别推理中的矛盾；
* 将规则结果转化为可理解反馈；
* 对照 rubric 辅助识别决策质量；
* 提取学生引用的证据。

LLM 的每项主观判断必须引用具体的：

* 对话内容；
* 决策表单；
* 方案比较；
* 风险判断；
* 复盘文本。

## 9.5 多解评分原则

评分不比较学生是否选择了预设答案，而评价：

1. 方案是否满足硬约束；
2. 证据是否充分；
3. 是否识别关键风险；
4. 是否考虑替代方案；
5. 取舍是否与目标一致；
6. 执行预案是否能够降低主要风险；
7. 是否能够解释承担了什么代价。

风险偏好不同的学生可以得到不同但合理的方案。

## 9.6 评分稳定性要求

进入教学验证前，评分系统需要完成：

* 同一输入重复评分测试；
* 与教师人工评分的一致性测试；
* 边界案例测试；
* 缺失信息测试；
* 无效引用测试；
* 提示词攻击测试；
* Agent 越权信息测试。

正式教学中，AI 反馈不应作为高风险成绩的唯一依据，教师应保留复核权。

# 十、学生端反馈结构

一次训练结束后，学生应看到：

## 10.1 你的决策

* 选择了什么；
* 满足了哪些硬约束；
* 承担了哪些主要风险；
* 哪些目标被优先满足；
* 哪些目标被主动放弃。

## 10.2 你的证据链

* 关键判断来自哪个角色；
* 使用了哪些数据；
* 哪些信息经过交叉验证；
* 哪些结论仍然依赖假设。

## 10.3 你的遗漏

* 未访问的关键角色；
* 未获得的关键信息；
* 未验证的冲突；
* 被忽略的硬约束；
* 缺少依据的判断；
* 未考虑的利益方。

## 10.4 后果解释

系统需要明确说明：

* 哪项决策改变了哪个状态；
* 哪个风险为何发生；
* 哪项预案降低了损失；
* 哪个信息如果提前获得，可能改变判断。

## 10.5 下一步建议

每次只提供 2–3 条具体、可操作的改进建议，例如：

* 下一次先确认接口故障是否影响核心支付链路；
* 在选择全面上线前，应先验证回滚时间是否满足事故处置要求；
* 比较方案时应明确延期损失和线上事故损失的不同时间尺度。

## 10.6 重试与迁移

产品应提供两类后续训练：

* 原场景重试：用于理解遗漏和调整策略；
* 平行场景训练：用于验证能力能否迁移，而不是只记住答案。

# 十一、竞赛 MVP 范围

## 11.1 MVP 的最小纵向闭环

首版必须完成：

* 1 个标杆场景；
* 4 个关键角色；
* 10–15 条场景事实；
* 其中 3–5 条高决策价值隐藏信息；
* 至少 2 组信息或利益冲突；
* 至少 2 个连续决策节点；
* 3 个核心状态变量；
* 1 张结构化决策表；
* 1 套确定性硬约束检查；
* 1 套证据化复盘；
* 1 份可导出的学生报告；
* 1 份教师讨论材料；
* 单次目标体验时长 30–40 分钟。

## 11.2 首版核心状态变量

首版优先显式维护：

1. 项目进度；
2. 质量或事故风险；
3. 组织支持或商业影响。

资源、收益、技术债等可以通过约束、事件和结果解释体现，不要求首版全部成为实时数值面板。

## 11.3 P0：形成可信闭环

必须完成：

* 场景真值表；
* 角色私有信息和权限；
* 信息获取与验证；
* 决策表单；
* 硬约束检查；
* 状态更新；
* 决策后果；
* 证据化复盘；
* 关键可靠性测试。

## 11.4 P1：提升真实感

验证 P0 后再增加：

* 信息可信度差异；
* 有限的多人会议冲突；
* 行为式关系反馈；
* 原场景重试与结果对比；
* 角色间有限互动；
* 更丰富的状态传导；
* 场景知识辅助。

## 11.5 P2：教学扩展

完成有效性验证后再考虑：

* 更多项目决策场景；
* 平行迁移场景；
* 教师后台；
* 班级管理；
* 课程配置；
* 场景编辑；
* 跨场景能力档案；
* 组织级教学报告。

## 11.6 第一版明确不做

* 不固定为 8 个 Agent；
* 不同时开发多个完整场景；
* 不用课程名称数量证明专业性；
* 不做复杂成长体系；
* 不做七维雷达图；
* 不做角色长期记忆；
* 不做纯剧情分支；
* 不做 0–100 实时信任分；
* 不做完全依赖大模型的黑盒评分；
* 不优先建设完整教师后台；
* 不扩展到人力、营销、供应链等泛管理场景；
* 不承诺管理科学与工程核心课程全覆盖。

# 十二、异常路径与系统处理原则

## 12.1 学生没有找到关键角色

系统可以允许学生提交，但复盘必须指出：

* 遗漏了哪个角色；
* 因此缺少什么证据；
* 该遗漏如何影响风险判断。

## 12.2 学生只聊天，不填写决策结构

系统应通过阶段提示要求学生将信息整理为：

* 事实；
* 目标；
* 约束；
* 方案；
* 风险。

聊天不能直接替代决策提交。

## 12.3 学生要求 Agent 直接给答案

Agent 可以：

* 提醒自己的角色立场；
* 提供权限范围内的信息；
* 反问学生的判断依据。

Agent 不得直接代替学生选择最终方案。

## 12.4 学生引用不存在的信息

系统应标记：

* 信息未在对话或材料中出现；
* 引用来源不成立；
* 对应推理缺少证据。

## 12.5 学生违反硬约束

系统不应简单阻止提交。

可以允许提交并展示后果，但必须明确指出：

* 违反了什么约束；
* 为什么方案不可执行；
* 哪些调整可能使方案重新成立。

## 12.6 学生未按时完成

系统应保留其现有过程，并在复盘中区分：

* 未完成信息获取；
* 未完成方案比较；
* 未提交最终决策；
* 时间配置不合理。

## 12.7 Agent 出现非预期矛盾

系统应记录：

* 冲突内容；
* 涉及角色；
* 是否影响关键事实；
* 是否需要从评分中排除；
* 是否触发场景质量告警。

# 十三、教育数据与治理原则

CareerCraft 会记录学生的对话、信息路径、决策和评分，因此必须遵守以下原则：

1. 明确告知学生系统记录哪些过程数据；
2. 只收集完成训练所必需的数据；
3. 学生能够看到评分引用的具体证据；
4. 教师能够复核 AI 辅助评价；
5. AI 不作为正式高风险成绩的唯一裁判；
6. 评分规则和主要评价维度应可解释；
7. 角色设定避免无关的性别、职业和人格刻板印象；
8. 学生数据不得被用于与教学目标无关的评价；
9. 用于研究或产品改进时，应进行必要的匿名化处理；
10. 系统错误不应转化为对学生能力的负面评价。

# 十四、产品验证框架

产品验证分为三个层次。

## 14.1 第一层：可用性

需要回答：

* 学生能否理解任务；
* 学生是否知道下一步做什么；
* 是否出现严重信息过载；
* 是否能在目标时间内完成；
* 学生能否理解状态变化和反馈；
* 产品是否出现大量无效等待和无目的聊天。

## 14.2 第二层：场景内表现

需要回答：

* 学生是否找到关键角色；
* 是否获得关键事实；
* 是否验证冲突信息；
* 是否识别硬约束；
* 是否比较多个方案；
* 是否提交可执行方案；
* 重试后是否改善。

## 14.3 第三层：能力迁移

需要回答：

* 学生完成一个场景后，能否在表面内容不同但能力结构相似的场景中表现更好；
* 学生是否能够主动识别新的关键角色；
* 是否减少约束遗漏；
* 是否提高方案可行率；
* 是否形成更完整的风险预案。

原场景重试只能证明学生能够纠正具体错误，不能单独证明能力发生迁移。

# 十五、核心产品假设与否决条件

## 假设一：主要缺口是决策过程能力

**假设：**

学生的主要问题不是完全缺少专业概念，而是缺少主动发现信息、识别约束和综合决策的机会。

**验证方式：**

观察学生失败原因，区分知识不足与决策过程不足。

**否决条件：**

多数学生无法完成任务的主要原因是缺少基础知识，产品实际变成知识补课工具。

## 假设二：分散信息能够改变学生行为

**假设：**

多角色分散信息会促使学生改变提问、判断和方案，而不是机械地问完所有角色。

**验证方式：**

分析学生的信息路径、提问策略和方案变化。

**否决条件：**

学生普遍按固定顺序问完角色，信息分散没有产生有效决策行为。

## 假设三：30–40 分钟可以形成完整闭环

**假设：**

学生可以在一节课或一次独立练习中完成信息获取、方案比较、决策和复盘。

**验证方式：**

测试 25、40、60 分钟版本。

**否决条件：**

多数学生无法在目标时间内完成，或大量时间消耗在无效对话和等待中。

## 假设四：混合评分能够稳定评价

**假设：**

规则结果与过程证据可以形成稳定、可信、可解释的评价。

**验证方式：**

建立标注样例，比较系统评分、重复评分和教师评分。

**否决条件：**

同一过程多次评价差异显著，或与教师判断长期严重不一致。

## 假设五：教师愿意采用

**假设：**

教师认为产品能够提供静态案例难以实现的训练价值，并愿意用于真实课程。

**验证方式：**

让教师实际布置、查看结果并组织复盘。

**否决条件：**

教师认可概念，但认为布置、讲评、解释和管理成本过高，不愿再次使用。

## 假设六：学生能够形成能力迁移

**假设：**

学生完成首个场景后，在平行场景中的决策过程会更加完整。

**验证方式：**

使用内容不同、结构相似的第二场景进行前后对比。

**否决条件：**

学生只记住了原场景信息，在新场景中没有明显改善。

# 十六、成功标准与指标

## 16.1 学习有效性

* 关键约束识别率；
* 关键事实获取率；
* 冲突信息验证率；
* 方案可行率；
* 风险预案完整度；
* 原场景二次决策改善率；
* 平行场景迁移改善率。

## 16.2 过程质量

* 平均有效访谈数；
* 无效访谈时间；
* 信息来源多样性；
* 关键事实获取效率；
* 方案比较完整度；
* 无依据判断比例；
* 决策表单完成率。

## 16.3 反馈价值

* 学生对遗漏解释的认可度；
* 学生对因果解释的理解度；
* 改进建议的可执行性评价；
* 原场景重试使用率；
* 平行场景继续训练率。

## 16.4 系统可靠性

* 相同输入评分一致性；
* 核心结果分支可复现性；
* 角色信息越权率；
* 非预期事实矛盾率；
* 关键事实一致性；
* 评分证据引用准确率；
* 场景状态计算错误率。

## 16.5 教学采用

* 教师愿意布置的场景比例；
* 教师再次使用意愿；
* 单次课堂可完成率；
* 教师对复盘报告的认可度；
* 课堂讨论材料可用性；
* 教师准备和批改时间变化。

# 十七、产品差异与创新表达

| 对比对象         | 常见做法                     | CareerCraft 的差异                         |
| ---------------- | ---------------------------- | ------------------------------------------ |
| 静态案例或作业   | 信息完整、一次提交、教师点评 | 学生主动获得信息，决策改变系统状态         |
| 单 Agent 教练    | 讲知识、提建议、回答问题     | 多个角色持有不同信息和目标，需要跨角色整合 |
| 传统经营沙盘     | 侧重财务或经营结果           | 同时记录信息路径、约束识别、决策证据和后果 |
| 角色扮演聊天     | 以沉浸感和对话体验为主       | 对话必须落到决策表单、硬约束和方案比较     |
| AI 作业评分      | 评价答案表达和完整度         | 规则先判断是否成立，AI 再基于过程证据解释  |
| 产品经理模拟面试 | 评价职业知识和表达           | 训练可迁移的复杂项目决策能力               |

## 最核心创新

> 将“在完整信息下分析案例”，升级为“在分散信息、冲突目标和动态后果中完成管理决策”的过程性仿真实训。

# 十八、统一对外表达

## 18.1 标准一句话定位

> CareerCraft 是面向管理科学与工程相关课程的复杂项目决策仿真实训工具。

## 18.2 痛点表达

> 传统管理案例通常会预先整理好问题和信息，学生很少有机会练习如何主动找到关键干系人、验证冲突信息，并在资源有限和多目标约束下承担决策后果。

## 18.3 解决方案表达

> CareerCraft 使用多个掌握不同信息、代表不同利益的 AI 干系人构建动态项目环境，要求学生主动访谈、验证证据、识别约束、比较方案并提交正式决策。

## 18.4 产品价值表达

> 系统记录学生找了谁、获得了什么信息、如何比较方案，以及决策造成了什么后果，并通过规则结果和过程证据提供可解释的复盘反馈。

## 18.5 专业关联表达

> CareerCraft 不覆盖管理科学与工程的全部课程，而是聚焦其中复杂项目决策、风险权衡、信息整合和系统思维的实训缺口。

## 18.6 30 秒答辩稿

管理科学与工程学生在课堂上学习过项目管理、风险分析和管理决策工具，但传统案例通常已经把问题和信息整理好了，学生很少练习如何主动发现信息、验证冲突观点并承担决策后果。

CareerCraft 将一个复杂项目拆分为多个拥有不同信息、立场和执行约束的 AI 干系人。学生需要在有限时间和资源下完成访谈、信息验证、约束识别、方案比较和风险决策。

系统不仅评价最终答案，还会记录学生的证据链、决策过程和项目后果，并据此提供可解释复盘。

我们不试图覆盖整个管理科学与工程专业，而是把一个最难通过静态课堂训练的能力做深：在信息不完全和多目标约束下完成复杂管理决策。

## 18.7 建议避免的表达

| 避免表达                       | 推荐替换                                       |
| ------------------------------ | ---------------------------------------------- |
| “管理科学与工程核心课程全覆盖” | “聚焦复杂项目决策、风险权衡与信息整合实训”     |
| “8 个 Agent 是核心创新”        | “分散信息与冲突目标驱动的决策过程仿真”         |
| “与真实产品经理工作一模一样”   | “在教学可控条件下还原真实项目决策的关键复杂性” |
| “AI 全自动精准评分”            | “规则结果与过程证据结合的可解释 AI 反馈”       |
| “没有标准答案”                 | “没有唯一最优答案，但存在明确约束和可行性边界” |
| “信任度实时量化协作”           | “角色行为和信息开放度随互动动态变化”           |
| “学生和 Agent 自由聊天”        | “学生通过角色访谈获得决策证据”                 |

# 十九、团队决策清单

以下内容视为 CareerCraft 5.0 版本的产品共识：

1. 产品只解决一个具体问题：信息不完全、多目标约束下的复杂项目决策训练；
2. 数字产品项目是首发教学载体，聚焦项目决策能力训练而非特定职业培训；
3. 多 Agent 是分散信息和利益冲突的实现手段，决策闭环才是产品本体；
4. 首版以一个标杆场景做深，不以场景数量、角色数量和功能数量证明完成度；
5. 每条隐藏信息都必须具有决策价值；
6. 每个角色都必须具有不可替代的功能；
7. 学生必须将对话转化为事实、目标、约束、方案和风险；
8. 场景没有唯一最优答案，但有明确事实、硬约束和可行性边界；
9. 场景真值表是 Agent、规则、状态和评分的共同依据；
10. Agent 不得创造关键事实或越权披露信息；
11. 评分以确定性规则和过程证据为基础，AI 只用于解释和辅助评价；
12. 学习有效性不能只用原场景重试证明，必须验证平行场景迁移；
13. 教师后台不是竞赛 MVP 的优先项，但教师最小交付物必须进入首版；
14. 首版目标时长为 30–40 分钟；
15. 在核心闭环和教师采用价值验证前，不扩展到泛管理学场景；
16. 所有对外表达统一突出：主动获取信息、约束下权衡、动态后果和证据化复盘。

# 二十、仍需通过原型验证的问题

| 开放问题                             | 建议验证方式                                 |
| ------------------------------------ | -------------------------------------------- |
| 访谈自由度与教学可控性如何平衡       | 对比自由聊天、引导式追问和结构化提问         |
| 4 个角色是否足以形成有效冲突         | 对比 4、5、6 个角色的完成率和信息负担        |
| 关键事实应如何设置披露条件           | 测试关键词、语义意图和证据前置三种方式       |
| 哪些状态必须数值化                   | 观察学生能否理解因果，以及是否出现刷数值行为 |
| 两个决策节点是否足够                 | 对比单次决策与连续决策的学习收益             |
| 规则评分和 LLM 反馈如何组合          | 建立教师标注样例并测试重复评分               |
| 学生是否理解“事实、预测和立场”的区别 | 分析信息板分类行为和复盘质量                 |
| 单场训练理想时长是多少               | 测试 25、40、60 分钟版本                     |
| 教师最需要哪种结果展示               | 测试个人报告、班级摘要和课堂讨论材料         |
| 学生能否迁移到新场景                 | 使用平行场景开展前后对比                     |

# 二十一、首轮验证必须回答的问题

首轮原型测试结束后，团队必须能够回答：

1. 学生是否会因为信息分散而改变提问、判断和方案？
2. 学生是否只是机械地把所有角色问一遍？
3. 学生的错误能否被定位为信息遗漏、约束遗漏、风险判断或推理问题？
4. 学生是否能够理解某项决策为何造成某项后果？
5. 混合评分是否比纯 LLM 评分更稳定、更可信？
6. 教师是否认为复盘结果可以用于课堂讲评？
7. 学生能否在 30–40 分钟内完成闭环？
8. 学生在平行场景中的表现是否有所改善？
9. Agent 是否能稳定遵守事实和信息权限？
10. 产品是否真正训练了决策能力，而不是只增加了聊天和剧情体验？
